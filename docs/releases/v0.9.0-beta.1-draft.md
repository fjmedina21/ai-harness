## Overview

AI Harness is an experimental local-first, provider-agnostic software-engineering
harness for one developer and one GitHub identity. It combines bounded agent
workflows, explicit host project authorization, exact human-reviewed isolated
changes and separately approved Podman validation.

The planned beta adds a static documentation portal and consolidates the existing
engineering and finite supervised repair foundations. Production autonomous
execution is not certified. The release gate is currently **BLOCKED**, including
real Phase 9C repair acceptance; see the [checklist](beta-release-checklist.md).

## Planned capabilities

- Sequential role-based orchestration and existing SDD/inspection workflows.
- Provider-neutral contracts, fixture-based offline operation and opt-in real
  adapters; OpenAI engineering has narrowly scoped historical live evidence.
  Anthropic inspection/tool-calling implementation is not live engineering acceptance.
- Host-owned tool registry and dispatcher, schema validation, Default Deny and
  finite request/token/time policies.
- Single GitHub owner authentication with OAuth + PKCE and macOS Keychain storage.
- Independent canonical project policy, file/operation/tool allowlists and budgets.
- Personal L2: exact diff review, typed `APPROVE`, fresh native macOS confirmation,
  one-time durable grant and fenced isolated application.
- Separate sandbox intent, closed snapshot transport, rootless pinned-image Podman
  actions and private durable evidence. Historical live acceptance is restricted
  to the documented fixed Node project/profile scope.
- SQLite persistence, CAS/lease fencing, effect-free continuation and conservative
  inspection of uncertain operations.
- Language-neutral discovery/profile/diagnostic contracts and finite repair with
  fresh approval for each patch and sandbox action. This is offline verified;
  real repair E2E remains blocked.
- A VitePress documentation portal with local search, contextual navigation,
  architecture diagrams and a documented manual release process.

## Requirements and installation

Source installation is the supported documented path; no package registry artifact
is promised. Use Node.js >=22, with Node 22.13+ or Node 24 for durable SQLite.
Development and CI target Node 24; pnpm is pinned to **12.21.0**.

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm harness --help
pnpm harness version
pnpm docs:build
pnpm docs:preview
```

These commands build an existing reviewed checkout. Do not install from a draft
tag. After an authorized release, the final notes must identify the exact verified
source/tag and artifact provenance before recommending a checkout command.

Authenticated operational workflows require a reviewed private host profile and
compatible GitHub App; macOS Keychain and native LocalAuthentication are the
supplied operational adapters. Podman validation additionally requires the exact
accepted, preprovisioned rootless Machine/image/action profile and separate native
sandbox approval. Real model calls require explicit provider/model/budget consent
and credentials supplied through the host, never through project content.

## Compatibility and migration

This is pre-1.0 experimental software; a minor milestone may contain incompatible
changes. Review [versioning](../VERSIONING.md) and [manual migration](../single-developer-migration.md)
before an upgrade. The current single-owner profile rejects previous account lists,
identity assignments and operational Team policies. Old grants are not converted
or rebound to another owner/project/policy.

Existing operational journals use schema v3; explicitly starting repair lazily adds
v4 repair tables. Read-only repair inspection does not upgrade a v3 journal.
Keep verified consistent private backups before an authorized upgrade; never
manually lower `user_version`, edit checksums or restore consumed grants.

Phase 9D itself does not change provider/runtime public contracts, authorization,
Podman controls or RepairCoordinator behavior. The final release owner must review
the complete diff from their installed version; these draft notes cannot establish
compatibility with every earlier internal milestone.

## Security and known issues

Authentication, authorization and approval are independent. Login cannot authorize
file writes, paid provider calls or sandbox execution. Patch grants and sandbox
grants are distinct and single-use. Generated source, manifests, model output and
diagnostics remain untrusted data.

Known limitations include:

- Real Phase 9C repair acceptance is pending; mocks and deterministic E2E do not
  establish live identity, human presence, isolation or model/toolchain correctness.
- Operational validation is restricted to exact approved fixed Node profiles.
  Detection of .NET, Java, Python, Go, Rust or another ecosystem does not provide
  a working or accepted toolchain.
- Container isolation is not infallible. Host/runtime/kernel/verifier compromise,
  same-UID parent-path races and guest staging mutability remain trust boundaries.
- SQLite, filesystem, providers and Podman are not one transaction. Prepared,
  Running or Uncertain effects require reconciliation; no automatic replay,
  rollback or external exactly-once guarantee exists.
- Original-project integration, Git-writing tools, auto-merge, autonomous deployment,
  Team/multiuser management and general remote execution are outside scope.
- Linux/Windows native credential adapters are not supplied. Remote Podman is deferred.
- Historical live acceptance expires and binds exact owner/project/code/runtime/
  profile/evidence; it cannot authorize a changed scope.

Do not place secrets in selected source or documentation. Raw profiles, journals,
keys, diffs and acceptance evidence stay private. See the [security model](../phase9-security.md),
[repair security](../phase9c-security.md) and [readiness assessment](../phase9d-release-readiness.md).
